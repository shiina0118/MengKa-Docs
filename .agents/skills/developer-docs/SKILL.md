# Meng Ka 开发者文档

## 读者与边界

文档面向使用 Meng Ka 的插件开发者和 API 接入者。后端闭源。读者应仅凭公开文档就能完成调用，不应需要阅读后端源码、理解 QQ 底层协议或复现后端实现。

以“调用方需要做什么、会得到什么、遇到问题如何处理”为组织依据。可以阅读实现来核实接口，但实现是核对依据，不是直接搬进文档的内容。已有页面中的内部细节不构成继续照抄的理由。

## 应当写清楚的内容

- 公开的 HTTP/WebSocket 接入方式、鉴权、请求与响应格式、事件格式。
- 实际对外暴露的字段名、类型、必填性、默认值、取值范围、空值与省略的区别，以及可确认的业务含义。
- 参数从哪个 API 或事件获取，调用顺序，关联标识如何保存和回传，以及调用方确实需要履行的状态管理责任。
- 成功和失败的可观察结果、公开错误、支持范围、大小限制、时效性与其他影响正确接入的条件。没有依据时，不承诺重试安全性、有效期或稳定性。
- 能直接用于接入的示例。沿用所在页面和相邻文档的格式，示例与参数、返回值保持一致。

“协议”不是禁词：Meng Ka 对外的 WebSocket 消息格式属于文档内容，QQ 底层通信协议属于实现细节。`protocol_id` 等真实 API 字段也必须保留并说明。

## 不写入公开文档的内容

- QQ 底层命令字、服务方法名、OIDB/SSO/TRPC 路由、子命令编号及其内部映射。
- protobuf/JCE/TLV 类型名、字段编号、二进制布局、封包与解包步骤、内部签名或加密计算过程。
- 后端函数、类、包、源码路径与行号、调用链、数据库结构、内部缓存或队列策略。
- 抓包、逆向、调试日志、实现推导过程，以及“源码中如何处理”的开发记录。

上述信息若确实以公开接口字段或取值的形式暴露，只描述调用方必须使用的外部契约，不继续展开其内部机制。不能为了避开内部术语而改名、删去真实字段、改变字段类型、修改 API，或虚构一个更友好的接口。

实现限制影响接入时，将其转换为可观察行为或操作要求。例如说明“调用方需保存本次响应供下一步使用”，无需解释“后端没有建立某种缓存”。后端主机路径、请求限制等直接影响调用的信息应保留。

## 不透明字段与未知字段

对凭据、游标、动作上下文或其他需原样回传的数据：

- 明确从哪个响应或事件字段获取、用于哪个请求参数、是否必填，以及已确认的格式要求。
- 要求原样保存和传递时，写明不要自行构造、解析或修改；无需公布底层消息类型、签名字段或未知字段的封装方式。
- Base64、字符串或对象等对外格式按事实说明；不要教读者解包、修改内部内容后再编码。
- 示例使用演示值或占位值时，明确调用时须替换为实际返回值，不把演示数据写成通用可用凭据。

对 `field_*` 等已暴露但业务含义尚未确认的字段，保留准确名称与可验证类型，不猜测语义，不从协议编号推导用途。可简短注明“含义暂未明确”；只有已确认可忽略或需原样传递时才给出相应建议。不要写成“内部结构未整理”等后端研发笔记。

## 改写示例

| 实现视角的表述 | 接入视角的表述 |
| --- | --- |
| `action_info` 是某 protobuf 消息的完整编码，保留签名和未知字段 | `action_info` 是事件提供的 Base64 动作凭据；调用对应接口时原样传入所选动作的值，无需解析或自行构造 |
| 后端不建立申请详情缓存 | 收到申请事件后，请保存处理申请所需的上下文，调用处理接口时一并传入 |
| 经由某内部服务命令执行操作 | 说明该接口执行的业务操作、前置条件和返回结果，省略内部命令 |
| 参见后端某文件中的处理函数 | 在本页写清参数规则，必要时链接到相关公开 API 或事件页面 |

示例只说明写法，不代表所有接口都有相同字段、格式或保存要求；具体内容必须核实。

## 修改与交付

1. 先确认本次涉及的公开 API 或事件契约，并检查相关 `src/` 页面及 `snippets/` 共享片段。核实实现不代表获准公开实现细节。
2. 围绕接入任务编写内容，将实现解释改写为必要的外部行为。无法核实的信息不编造，也不把内部推测当成公开保证。
3. 检查本次变更，包括示例、注释、共享片段和生成模板：读者是否需要后端源码才能使用？是否夹带底层协议或内部机制？原样回传字段的来源与去向是否清楚？接入必需的真实字段和限制是否保留？
4. 检查链接、示例与字段说明的一致性；涉及站点页面、导航、组件或片段时，按仓库现有方式运行构建并报告结果。

仅处理本次任务涉及的内容；发现其他页面的问题可向用户指出，不擅自全库重写。用户明确要求内部研发文档时，单独放在其指定的内部位置，不混入公开站点。不要自行创建包含闭源实现的新“内部说明”来安置删去的内容。
